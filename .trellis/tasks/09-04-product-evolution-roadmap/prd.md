# BalanceHub 功能优化与拓展路线图

## Goal

在不把 BalanceHub 扩张为中转服务端的前提下，把现有中转站、API Key、动态模型、测活、Agent CLI、会话和后台任务能力组织成六条可执行的产品工作流，使用户能够选择可用配置、管理 Agent 环境与运行会话、继续历史工作、定位环境问题、完成中转站接入并按事实获得提醒。

## Background

- 当前应用已经具备中转站与多 Key 管理、动态模型获取、真实 CLI 测活、临时 CLI、历史会话、后台任务、公告、通知和跨平台终端能力。
- Provider 协议目录、Agent CLI 注册表、Terminal 目录、统一网络层、Provider 事务和会话适配器继续作为唯一真源。
- 用户已确认六个产品方向均需要推进，并明确将“可用性决策中心”后置，第一项交付改为“Agent 环境与运行时中心”。
- 现有后台任务、调度器、会话索引和前后端类型文件已接近职责上限；功能开发必须同步收敛直接相关边界。
- 用户已确认外部 Agent 会话采用“官方 Hook + PID/TTY 补证 + Agent 会话文件富化 + 持久事件队列”的混合观察方案，精确终端定位按平台和终端能力降级。
- 用户要求 Hook 集成可由用户逐 Agent、逐运行环境手动安装、启停、删除、检查和修复，不能退化为启动时静默写入的一次性配置。

## Requirements

### R1. 任务与交付边界

- 父任务维护共同目标、能力边界、依赖顺序和最终集成验收。
- 六个方向分别使用子任务规划、实现、验证和回滚，不能在一个长期改动中同时铺开。
- 每个子任务进入实现前必须具备独立 PRD、技术设计、执行清单和检查上下文。

### R2. 可用性决策中心

- 按模型比较 Provider、账号、Key、额度、最近测活、延迟、数据新鲜度和 Agent 绑定。
- 第一版只投影本地已有事实；打开、筛选和排序不得自动刷新、运行 CLI 测活或修改配置。
- 对没有 Key 级证据的组合明确展示“未验证”或“未知”，不得把 Provider 级模型列表或历史测活错误归属到任意 Key。
- 用户可以从候选项进入现有临时 CLI、选择当前 Key、预览并确认 Agent 默认配置、模型详情和测活详情。
- 排序理由、证据来源和数据新鲜度必须可解释，业务判断由 Rust 返回。
- 入口采用“搜索区上下文入口 -> 独立主体工作区 -> 返回并恢复原面板上下文”；不设置永久并列 Tab，也不使用大型弹窗。

### R3. Agent 会话工作台

- 把 Agent、工作目录、会话搜索、筛选、详情、恢复和运行实例组织为独立工作流，不再依附临时 CLI 启动弹窗。
- 结果始终以会话为单位；工具调用和工具输出可在详情中折叠，但不进入全文检索。
- 各 Agent 保持独立解析器、索引与能力边界；只对声明支持会话能力的动态 Agent 展示相关操作。

### R3A. Agent 环境、运行时与 Hook 管理

- 以 Agent 安装与运行环境为根，统一只读盘点配置文件、Skills、Plugin/Extension、MCP、Hook 和 Status UI，展示来源、scope、实际/有效状态、信任、覆盖关系与诊断。
- 展示每个安装实例的本地版本、最新稳定版本、版本来源和检查时间；首版只比较并链接官方来源，不自动升级 Agent。
- 提供配置文件定位、打开、复制路径和有界只读预览；不依赖“切换默认 CLI 配置”才能查看，也不接受前端任意路径。
- 保留现有临时 CLI 的启动登记、Provider/账号/Key 来源、终端 locator、PID、退出码和状态文件证据，但将其重构为统一 `AgentRuntimeSession` 的 BalanceHub 启动来源。
- 删除“临时 CLI 实例”作为独立产品域、独立列表和独立前端真源；统一运行时投影稳定后，顶栏、Provider 卡片和会话工作台只消费同一份 Rust IPC 合同。
- 用户级官方 Hook 作为外部 Agent 会话的实时主证据；桥接 helper 只保留允许的运行元数据，并通过有界、原子的 App-data spool 支持 App 未运行期间的事件留存。
- BalanceHub 启动会话必须注入命名空间关联 ID，使状态文件与 Hook 事件稳定合并为一条记录；不得按 cwd、时间窗口、可执行文件名或当前默认 Provider 猜测关联。
- 外部会话没有精确 PID、终端或 Provider 证据时保持字段缺失；证据过期进入 `unknown`，不得伪造为正常结束、失败或可激活。
- Hook 管理必须提供 `inspect`、`plan`、`install`、`remove`、`enable`、`disable`、`health`、`repair`、`verify`；安装成功仅表示 `installed_unverified`，收到下一次真实 Agent 事件后才能标记 `healthy`。
- Hook 管理必须在 Agent 管理界面中按 Agent 和运行环境展示，允许用户手动添加、删除、启用、禁用和修复 BalanceHub 注入项；每次写入前展示将变更的节点与冲突，不使用启动时静默注入代替可管理配置。
- Hook 写入只修改能证明由 BalanceHub 拥有的节点或独立资源；每次变更先展示结构化计划并校验 revision，发生用户修改或归属冲突时不得覆盖或删除。
- BalanceHub 不接管 Agent 配置，也不与其他工具争抢写权限：检测到 owned 节点缺失、漂移、无权限或冲突时只报告事实并提供手动修复；无法证明可安全修改时保持磁盘现状，不默认自动恢复。
- `inspect`、`health`、`verify`、启动扫描和文件监听严格只读；`repair` 只生成计划，任何 apply 都必须来自当前用户确认。不修改 trust store、权限策略、系统/受管配置、Shell profile 或非 BalanceHub-owned 的 Hook、MCP、Statusline 和插件设置。
- Hook helper 失败、App 未运行、spool 满、配置未信任或事件 schema 不兼容都不得阻止 Agent CLI 自身运行。

### R4. 一键诊断中心

- 只读检查代理、系统证书、Agent CLI、终端、Agent 配置、站点协议和更新链路。
- 每项检查有独立状态、耗时、证据、适用平台和建议；部分失败不能中断其他检查。
- 支持取消、超时、增量进度以及默认脱敏的报告预览与导出，且运行前后不能改变业务配置或 updater 状态。

### R5. 中转站接入向导

- 用单一流程编排地址规范化、协议探测、认证说明、凭据补全、连接/能力检查、重复冲突计划和最终保存。
- 保存前必须展示将新建卡片、合并 Key、独立新增还是覆盖；重复判断和允许动作只来自 Rust。
- 向导替换现有新增流程，不保留平行的旧入口；未经独立确认不得静默创建远程 Key 或产生其他远端副作用。

### R6. 自动化规则中心

- 围绕余额阈值、连续测活失败、签到失败、模型变化和 Key 状态定义通知规则。
- 规则具备作用域、条件、冷却期、启停、执行时机和有界历史；未知或过期事实不触发提醒。
- 第一版仅发送通知，不自动切换 Provider/Key、修改 Agent 配置、执行脚本或发送付费请求。

### R7. 共同工程约束

- Rust 是协议、动作能力、事实投影、诊断和规则语义的唯一真源；TypeScript 只维护接收结构和 UI 状态。
- 模型、Agent 和终端必须动态发现，通用代码不得写死当前四个 Agent。
- 网络、IPC 和外部进程操作必须有超时、取消或后端任务状态，并在成功、失败、取消和过期时释放忙碌状态。
- 优先拆分直接受影响的过重模块，不新增 `manager`、`common`、`helpers`、`utils` 等无明确职责目录。
- macOS、Linux、Windows 的行为、适用性和降级路径分别验证。
- IPC 不返回明文凭据；诊断脱敏必须在 Rust 返回前完成。

## Delivery Order

1. 先交付 Agent 环境只读盘点、统一运行时合同、现有临时 CLI 证据适配、Hook helper/spool 和 Hook 管理闭环。
2. Agent 会话工作台与一键诊断中心在文件边界不重叠时可并行；会话工作台只消费统一运行时投影。
3. 可用性决策中心后置，届时冻结并交付可用性事实投影和决策工作区。
4. 诊断结果契约稳定后，接入向导复用其检查结果语义并替换旧新增流程。
5. 可用性事实投影稳定后实现通知型自动化规则中心。
6. 完成跨功能、迁移、性能、隐私及三端集成验收；WSL 按独立后续任务验收。

## Acceptance Criteria

- [ ] 六个方向均有独立子任务、明确前置依赖、范围、验收标准和回滚边界。
- [ ] 第一阶段的数据来源、未知语义、刷新语义、排序层级、入口和直接操作都有可执行设计。
- [ ] 从面板进入和返回决策工作区时，原搜索、滚动位置和焦点得到恢复；面板搜索与模型搜索互不覆盖。
- [ ] 可用性事实投影以 Rust 为唯一真源，包含来源、观测时间、新鲜度和 revision，且不向前端发送凭据。
- [ ] Agent 会话工作台、诊断中心、接入向导和自动化规则中心均可在不依赖其他未声明功能的情况下独立验收。
- [ ] BalanceHub 启动与外部 Hook 发现的 Agent 会话通过统一 Rust 投影展示；同一 BalanceHub 会话不重复，外部未知字段不被虚构。
- [ ] 当前 Agent 的配置、Skills、Plugin/Extension、MCP、Hook、Status UI 和安装版本可按环境只读盘点；配置可定位、打开和有界预览，版本失败不会伪装成“已是最新”。
- [ ] Hook 管理具备手动安装、启停、删除、健康检查、修复和真实事件验证闭环，且只修改 BalanceHub-owned 资源。
- [ ] Hook 被外部修改、删除或阻止写入时，App 不自动抢回配置、不覆盖用户内容；无法无冲突修复时清楚说明原因并保持原状。
- [ ] 启动扫描、健康检查、取消、冲突、unsupported、受管配置、只读文件和权限不足均保持原配置字节不变，也不请求管理员权限扩大范围。
- [ ] App 未运行期间的 Hook 事件可在重启后有界消费；helper、spool 或 Hook 配置异常不阻止 Agent CLI 运行。
- [ ] 后台任务、会话取消、索引锁和 scheduler 的共享风险在对应首个消费者实施前得到处理并有回归测试。
- [ ] 大规模数据、异步取消、存储迁移、隐私、macOS、Linux 和 Windows 均有明确验证矩阵。
- [ ] 每个子任务经独立检查后再进入下一个依赖阶段，父任务最后执行跨功能集成检查。
- [ ] 用户审阅本次最终规划摘要后，再单独授权启动第一个实现子任务。

## Out of Scope

- 通用 OAuth/WebView 登录自动化。
- Cloudflare 或其他通用反爬、人机验证绕过。
- 内置中转代理、透明转发或自动故障切换服务端。
- 未经用户确认自动修改 Agent 默认配置、切换 Key、创建远程 Key 或发起收费请求。
- 第一版自动化规则执行任意脚本或业务修复动作。
- 第一阶段对外部终端会话执行 kill、输入注入、审批接管或承诺三端精确窗口定位。
- 第一阶段对 Skills、Plugin/Extension、MCP、Status UI 执行安装、删除、同步、迁移、通用启停或自动升级；只有 BalanceHub 自己的 Hook 注入项具备受管写操作。
- 将原生 Windows 支持描述为 WSL 支持；WSL 发行版、Linux home、路径和 guest PID 另行实现与验收。
